## The Two-Tier Proposal Model

PropCRM's proposal lifecycle has TWO distinct actors and TWO distinct document grades.

### Tier 1 — Broker Proposal (Communication-grade)

**Purpose:** Initial offer from broker to buyer, signals intent and key terms.

**Characteristics:**
- Generated BY broker IN PropCRM via ProposalBuilderDialog
- Captured as a PDF (auto-generated on Save)
- Contains broker-relevant terms only: net price, payment plan, DLD handling, validity
- **Excludes** developer-internal fees (developer admin fees, OQOOD, trustee) — these are dev's concern, not broker's narrative
- **Excludes** broker's own commission visibility — separate concern
- Distributed via:
  - Download from app
  - Email from app (PDF attached, not inline body)
- **Versioning:** V1, V2, V3... each new version supersedes previous
- **Not legally binding** — communication artifact only

### Tier 2 — Developer Proposal (Legal-grade)

**Purpose:** Final binding proposal the buyer will accept and sign.

**Characteristics:**
- Generated BY developer, OUTSIDE PropCRM (developer's own system or paperwork)
- Uploaded to PropCRM as a document (PDF/image)
- Contains complete legal terms (developer fees, trustee, OQOOD, admin charges, etc.)
- **Supersedes** broker's proposal versions
- **Multiple developer proposals possible** (counter-proposals, revisions)
- This is what buyer signs

---

## Why This Distinction Matters

### For brokers
- Broker can put forward terms quickly (Tier 1) without waiting for developer paperwork
- Broker's PDF is a clean negotiation artifact
- Broker isn't liable for developer-internal fees they don't control

### For audit
- Both tiers tracked in `proposals` table
- Clear chain: Broker V1 → Broker V2 → Broker V3 → Developer V4 (final, signed)
- Each version preserved with metadata about source

### For investors
- Demonstrates real understanding of UAE brokerage workflow
- Architectural rigor — doesn't conflate communication with legal artifacts
- Future-proofs for multi-developer scenarios

## Data Model Changes Required (Phase 2)

### New columns on `proposals` table

```sql
ALTER TABLE proposals ADD COLUMN proposal_source TEXT
  CHECK (proposal_source IN ('broker_generated', 'developer_uploaded'));

ALTER TABLE proposals ADD COLUMN document_url TEXT;  -- Supabase Storage path to PDF
ALTER TABLE proposals ADD COLUMN document_uploaded_at TIMESTAMPTZ;
ALTER TABLE proposals ADD COLUMN document_uploaded_by UUID REFERENCES profiles(id);

ALTER TABLE proposals ADD COLUMN supersedes_version INTEGER;  -- which version this replaces
```

### New behavior

**Save broker proposal:**
1. Capture form state in `structured_data` (current behavior)
2. **NEW:** Generate PDF from structured_data using template
3. **NEW:** Save PDF to Supabase Storage at `proposals/{opp_id}/V{version}.pdf`
4. **NEW:** Store URL in `document_url`
5. **NEW:** Mark `proposal_source = 'broker_generated'`
6. Existing: increment version, supersede previous

**Upload developer proposal:**
1. **NEW UI:** "Upload Developer Proposal" button (separate from "Send Revised")
2. Broker uploads PDF directly
3. PDF stored in Supabase Storage
4. New proposal row with `proposal_source = 'developer_uploaded'`
5. Document metadata: who, when, optional notes
6. **Optional:** OCR/AI extraction of key terms (Phase 2.5+)

### UI Changes

**Proposals tab Excel table — additional columns:**
- "Source" — broker icon vs developer icon
- "Document" — PDF link (click to download)

**Proposal Builder dialog:**
- Save button text changes: "Save & Generate PDF" instead of "Save (don't email)"
- After save: show "✅ PDF generated. Email it to the buyer or download."
- Two follow-up buttons: "📥 Download PDF" / "✉ Email PDF as attachment"
- **Remove** the inline email body preview (no longer needed)

## Email Behavior Change

### Current (Phase 1)
- "Save & Email" → sends email with inline body containing proposal terms
- Body is auto-generated from form state

### Phase 2
- Save generates PDF
- Email is OPTIONAL and SEPARATE action
- When emailing: PDF is the attachment, email body is brief cover note ("Please find attached our proposal V3...")
- Same PDF can be re-sent or downloaded any time

## Versioning Semantics

### Broker-generated (Tier 1)
```
V1 (broker) → V2 (broker) → V3 (broker)
                 ↑              ↑
                 supersedes     supersedes
```

### Developer-uploaded (Tier 2)
```
V3 (broker) → V4 (developer uploaded)
                 ↑
                 supersedes V3
                 → BUT: developer can also have their own V4a, V4b if they iterate
```

**Decision needed for Phase 2:** Do we use SAME version numbering or distinguish?

Option A — Single sequence: V1 → V2 → V3 (broker) → V4 (dev) → V5 (dev)
Option B — Separate sequences: BV1 → BV2 → BV3 → DV1 → DV2

**Founder's instinct (Brahma Lipi reading):** Option A — single sequence, source column distinguishes.
