Data Architecture06
Multi-Tenant Security

Defense-in-depth, by design

Security isn't a promise — it's enforced by architecture. Two independent layers guard every tenant's data, so a gap in one is caught by the other.

① Two-Tier Identity
Platform Operators (run the platform) are architecturally separate from Tenant Users (use the CRM). Platform staff cannot read tenant CRM data.
② Group → Branch → Data
A Group is the umbrella; each Branch is a trade-license entity with isolated data. Visibility rules are configurable per group.
③ Capability Model
role_capabilities — a per-tenant table mapping role → capability. Configurable without code changes; reads like a spreadsheet, audits cleanly.
④ RLS + App-Layer Floor
Row-Level Security scopes every query by company_id. Crown-jewel data (commission, margins) is enforced in both RLS and app layer.
🔒

"What stops your team reading our pipeline?" → Architecture won't let us. Tenant data is scoped by Postgres RLS on every table; platform staff hold a separate identity with no data access.

✨ AI Layer

A single shared aiInvoke gateway routes all AI calls through one secured endpoint — used by AI Coach, proposal matching, reminders, and PropPulse verification.

  • AI Coach — ranks deals, recommends next moves with confidence levels
  • PropPulse Agent — verifies project data from public sources
  • Proposal Match — AI-assisted unit/buyer fit

One gateway = one place to secure, rate-limit, swap models, and audit. AI is a capability of the platform, not scattered integrations.
